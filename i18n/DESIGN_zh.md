# VIDEO.md 的设计思路

[SPEC_zh.md](SPEC_zh.md) 讲 VIDEO.md 拆片包长什么样、怎么校验。这一页讲为什么长这样：要解决什么问题，每个设计决定背后的考虑，借鉴了哪些现成的做法，以及它给使用者带来什么。

## 一句话

VIDEO.md 是一种**给模型读的视频拆解格式**。每个技能有一个 `SKILL.md`，每条视频也有一个 `VIDEO.md`：从一张百来 token 的卡片开始，逐层展开到单个镜头，每一层都写明自己有多大、里面哪些是看到的、哪些是推断的。

打个比方：卡片是这条视频的身份证，一眼看清它是什么、怎么做的、有多确定；整个包是它的档案，从概览、时间线到单个镜头，要查哪一层就翻到哪一层，不用整本读完。

## 要解决的问题

拆解一条视频，工具会产出大量东西：逐镜的测量值、制作方式的概率、证据、字幕时间轴、音效位置、复刻提示词、截图、分轨音频。这些数据有三类读者，需求完全不同：

| 读者 | 要什么 | 怕什么 |
|---|---|---|
| 人 | 结论、看点、照着做的步骤 | 看不懂、信息太散 |
| 模型 / agent | 能回答用户问题的那部分事实 | 上下文太贵、在细节里迷路、把推断当事实 |
| 下游程序 | 稳定的字段和取值 | 格式悄悄变了、解析正文 |

给人看的有 `report.html`，给程序的有 `breakdown.json`。缺的是中间那个：模型。

把 `breakdown.json` 直接交给模型行不通。一条 3 分钟口播约 19 万 token，一条 75 镜的影视解说约 24 万。模型每回答一个问题都读一遍，又贵又慢；而且 JSON 里测量值、推断和最终结论平铺在一起，模型很容易把「工具猜 41% 是录屏」读成「这是录屏」。

把 `report.md` 交给模型也不对。报告是按人的阅读顺序写的，有折叠、有修辞、有重复的引导语，模型拿不到稳定的结构，也没法只读其中一段。

VIDEO.md 就是为模型这一类读者设计的。

## 借鉴了什么

VIDEO.md 没有发明新东西，它把几种已经被证明好用的做法组合在一起。

### Agent Skills：逐层展开

Agent Skill 的结构是：`SKILL.md` 开头的 `name` / `description` 常驻上下文，只有几十个 token；agent 判断用得上时才读正文；正文再指向 `references/` 下的文件，需要时才打开。用多少读多少，这叫渐进式展开（progressive disclosure）。

VIDEO.md 照搬了这个结构，只是把「一项能力」换成了「一条视频」：

| Agent Skill | VIDEO.md |
|---|---|
| `SKILL.md` 前置信息（name、description） | `VIDEO.md` 前置信息：卡片（name、description、制作占比、置信度） |
| `SKILL.md` 正文：流程和指引 | `VIDEO.md` 正文：结论、不确定点、地图 |
| `references/*.md`：按需打开 | `video/*.md`：按主题按需打开 |
| 脚本、资源文件 | `breakdown.json`、截图、分轨音频 |

区别在于 VIDEO.md 多走了一步：每个文件的前置信息里写着自己的 token 数，地图里也列着。Skill 只告诉 agent 「这里有什么」，VIDEO.md 还告诉它「打开要花多少」。模型可以在读之前就权衡值不值得。

### DSL：一行一镜的时间线

时间线是整个包的主干。它没有用 JSON 数组，也没有用 Markdown 表格，而是一个很小的行格式：

```
#07 16.2-18.5 | seen 男子讲话，画面上弹出多张聊天截图 | cam 固定 | made~ 屏幕录制/截图(screen_capture) 41% | flag 低置信
```

这是一种很窄的领域语言（DSL），思路和 SRT 字幕、EDL 剪辑表、日志格式一样：一行一条记录，开头是编号和时间，后面是 `键 值` 对。选它的原因：

- **省 token。** 同样的信息写成 JSON，键名、引号、括号要占掉一大半。75 镜的时间线约 3.5k token，模型可以一次读完全片。
- **人和模型都能直接读。** 不需要渲染，打开就能看懂；模型生成和改写也不容易出错。
- **程序能稳定解析。** 语法只有三条：行首 `#编号 起-止`，字段用 ` | ` 分隔，第一个空格前是键。值里保证不出现 `|`。参考实现不到二十行。
- **能表达「推断」。** 键名后带 `~`（`made~`、`real~`）表示这是工具推断的，不带的是画面里看到或直接测得的。这个区分写在语法里，不用靠模型去理解上下文。

但 VIDEO.md 只在时间线这一处用了 DSL。卡片和单镜数据用 YAML 前置信息，有 JSON Schema 约束；细节说明用普通 Markdown。小语法只放在最需要密度的地方，其他地方用大家都会读的格式。

### 其他

- **Markdown + YAML 前置信息**：静态站点生成器（Jekyll、Hugo）和 Agent Skills 都这么用。正文给模型读，前置信息给程序读，一个文件两种用途。
- **JSON Schema**：卡片、主题文件、镜头文件的前置信息都有 schema，`videomd check` 用它校验。
- **目录即包**：和 Skill 一样，一个目录就是一个完整的包，没有打包格式、没有索引数据库，复制、压缩、放进 git 都行。

## 设计决定

### 分四层，每层比上一层贵一个量级

| 层 | 大小 | 够回答什么 |
|---|---|---|
| L0 卡片 | 约 150 token | 这是什么视频、怎么做的、有多确定 |
| L1 概览和地图 | 约 1–2k | 结论、复刻概要、哪里不确定、下一步该读哪个文件 |
| L2 主题文件 | 几百到几千 | 某一方面（时间线、声音、包装、复刻方案）的全部信息 |
| L3 单镜文件 | 约 500–1000 | 某一镜看得到什么、推断是什么、依据、提示词、帧图 |
| L4 原始数据 | 几十万 | 程序用 |

以 rea-video 生成的包为例，大多数问题（「这条怎么做的」「要准备什么素材」「哪几镜要复核」）读到 L1 就能回答，按镜头回答再加上时间线，一共约 4k token。只有核实某一镜时才需要打开 L3。

分层的依据是问题的粒度：用户先问整体，再问某一方面，最后才问某一镜。每一层正好对应一种粒度的问题。

### 读之前就知道代价

每个文件的前置信息里都有 `tokens`，地图表格里也有一列。这看起来是个小细节，但它改变了模型读文件的方式：不是「打开看看」，而是「这个问题值得花 14k token 去读复刻方案吗，还是时间线里的 `remake` 字段就够了」。

### 看到的和推断的分开

这是 VIDEO.md 最重要的一条规矩。视频拆解里有两种性质完全不同的信息：

- **看到的**：画面里有一个人在讲话、右上角有标题、镜头是固定机位。对着截图就能核实。
- **推断的**：这一镜是 AI 生成的（72%），依据是噪声分布和帧率。肉眼不一定能核实。

两者混在一起，模型就会把推断当事实告诉用户，用户也分不清哪句该信。所以 VIDEO.md 在三个地方把它们分开：时间线用 `~` 标出推断的键；单镜文件分成「画面里看得到的」和「工具推断的制作方式」两节；推断的字段统一放在 `inferred` 下，附概率、次选和 `decided_by`（`tools` 工具 / `model` 看图模型 / `agent` / `human` 人）。两者对不上时，以截图为准。

### 时间线是主干

视频天然是线性的，几乎所有问题最后都会落到「第几秒、第几镜」。所以时间线是唯一一个一定要读完整的 L2 文件，其他主题文件和单镜文件都通过镜头编号挂在它上面。时间线里的 `flag` 字段直接标出要复核的镜头，模型扫一遍就知道该去看哪几张图。

### 格式固定，内容开放

能被程序依赖的部分是固定的：前置信息的字段、时间线的语法、类别 id（`live_action`、`ai_video`……）。可以增加的部分是开放的：时间线可以加新键、可以加新的主题文件、叠加层的取值可以增加。规则是读的一方遇到不认识的东西就忽略，不报错。只加不改时版本号不变，改了已有字段的含义才升 `videomd:` 版本。

这样拆解能力变强时（比如加了新的拍法维度），旧的读取方不用跟着改。

### 给模型的值跟语言走，给程序的 id 保持稳定

时间线里写的是「屏幕录制/截图」还是 screen capture，跟着包的语言走，因为它是给模型读的。但括号里的 `(screen_capture)` 和单镜前置信息里的 `inferred.made` 永远是稳定的英文 id，程序只认这个。

## 好处和价值

**对 agent：**
- 回答一个问题的成本从几十万 token 降到几千，可以在同一个对话里拆多条视频、来回追问。
- 不需要理解 rea-video 的内部数据结构，读 Markdown 就行。
- 推断和事实分开，转述给用户时不容易说过头。
- 地图和 token 数让它自己决定读多深，不用写死读取流程。

**对下游程序：**
- 有 schema、有校验命令、有参考读取实现（`videomd.read()`），可以只依赖前置信息和时间线，不碰正文和 `breakdown.json`。
- 新增内容不会弄坏已有的解析。

**对人：**
- 拆片包本身就是能直接读的 Markdown，不需要工具也能翻。
- 判断来源写在包里（`readers`、`decided_by`），看得出哪些结论是机器测的、哪些是看图确认过的、哪些是用户纠正过的。

**对整个流程：**
- 拆解和使用解耦。拆解工具可以换、可以升级，只要输出合格的 VIDEO.md，读的一方不受影响；反过来也一样，任何能读 Markdown 的 agent 都能用拆解结果。
- 复核有了落点。低置信镜头在时间线上标着，复核结果写回后重新生成包，`decided_by` 跟着变。

## VIDEO.md 不是什么

- **不是报告。** 报告写给人，讲故事、给步骤；VIDEO.md 写给模型，讲事实、给结构。两者从同一份数据生成，内容一致，组织方式不同。
- **不是剪辑工程文件。** EDL、OpenTimelineIO 描述的是「片段怎么拼成成片」，给剪辑软件用。VIDEO.md 描述的是「这条视频里有什么、是怎么做出来的」，给理解和复刻用。
- **不是数据库。** 没有查询语言，没有索引。一条视频一个目录，靠地图和文件名找东西。

## 和其他做法的对比

| 做法 | 问题 |
|---|---|
| 直接给模型 `breakdown.json` | 太大；测量、推断、结论混在一起 |
| 直接给模型报告 | 没有稳定结构，没法只读一部分 |
| 每次让模型自己去读视频 | 贵、慢、不可复现，也拿不到帧率、噪声、元数据这类肉眼看不到的证据 |
| 一个大 Markdown 文件 | 要么太长读不完，要么太短不够用；无法按需展开 |
| 纯 JSON API | 程序友好，但模型读起来浪费 token，人也看不了 |

VIDEO.md 的做法是不在这些里面选一个，而是分层：上层给模型、中层给模型和程序、底层给程序。
